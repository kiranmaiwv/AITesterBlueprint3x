QA Buddy AI v1.0

Hybrid Retrieval-Augmented Generation for QA Engineering Teams

Overview

QA Buddy AI is a Hybrid RAG system built for QA engineering teams. It allows engineers to ask natural language questions and get cited answers grounded in their actual codebases — Selenium frameworks, Playwright tests, JIRA tickets, test case repositories, PRDs, meeting notes, and Jenkins logs.

Key Capabilities

  • Multi-source RAG — 10 data sources indexed into a single vector database
  • Cited answers — Every response includes source references with folder and file paths
  • Streaming responses — Real-time token-by-token answers via Server-Sent Events
  • JIRA integration — Fetch tickets via JQL, index them, and query across them
  • Code-aware chunking — Semantic chunking per function/class, not arbitrary character splits
  • Deployed on Vercel — Serverless backend, globally distributed static frontend

Architecture

The system follows a three-tier architecture adapted for Vercel's serverless model:

  • Frontend — React 19 + Vite SPA deployed as static files on Vercel's CDN
  • API — Python Flask serverless function via Vercel's Python runtime
  • Cloud Services — GROQ (LLM), OpenAI (embeddings), Qdrant Cloud (vector DB), JIRA Cloud (tickets)

Unlike a Docker-based deployment, there are no local services running. All heavy computation (embeddings, LLM inference, vector search) is handled by managed cloud APIs. This makes the system zero-maintenance and globally scalable.

The ingestion pipeline runs locally via scripts/seed_qdrant.py, which reads the 10 data folders, chunks each file, generates embeddings via OpenAI, and pushes the vectors to Qdrant Cloud.

Backend Implementation

The backend is a Flask application served as a single Python file at api/index.py. This is the standard Vercel Python serverless pattern.

Chat Streaming (SSE)

The /api/chat endpoint uses Server-Sent Events to stream the response. The flow is:

  1. Receive {query, history} from the frontend
  2. Embed the query via OpenAI text-embedding-3-small
  3. Search Qdrant Cloud for the top-4 most relevant chunks
  4. Build a GROQ prompt with system instructions, retrieved context, conversation history, and the query
  5. Stream the LLM response token-by-token as data: {"type":"token","content":"..."}
  6. After completion, send data: {"type":"sources","content":[...]} with source metadata

Frontend Implementation

The frontend is a React 19 + TypeScript single-page application built with Vite 6. It's deployed as static assets on Vercel's CDN, with all /api/* requests proxied to the Python serverless function via vercel.json rewrites.

Component Architecture

  • App.tsx — Root component, manages GROQ key state
  • ChatWindow.tsx — Message list + header with settings button + empty state with example queries
  • ChatInput.tsx — Auto-resizing textarea with Enter-to-submit, Shift+Enter for newline
  • SourceCard.tsx — Grid of cited sources with file path, folder label, confidence score
  • SettingsPanel.tsx — Modal overlay with System status tab and Connection configuration tab

SSE Client

Chat streaming uses the Fetch API with response.body.getReader() to read the SSE stream. The streamChat generator function in src/api/chat.ts yields parsed events, which are consumed by the useChat hook to update message state.

export async function* streamChat(query, history) {
  const response = await fetch('/api/chat', { method:'POST', body: JSON.stringify({query, history}) })
  const reader = response.body.getReader()
  const decoder = new TextDecoder()
  let buffer = ''
  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    buffer += decoder.decode(value, { stream: true })
    for (const line of buffer.split('\n')) {
      if (!line.startsWith('data: ')) continue
      yield JSON.parse(line.slice(6))
    }
    buffer = ''
  }
}

RAG Pipeline

The RAG pipeline is intentionally simple but effective, using API-based services instead of local models:

1. Query Embedding

The user's question is embedded using OpenAI text-embedding-3-small (768 dimensions). This model was selected over alternatives because it requires zero local compute — it's a simple API call, making it ideal for Vercel's serverless constraints.

2. Vector Search

The query vector is sent to Qdrant Cloud, which performs a cosine similarity search against all indexed chunks. The top 4 most semantically similar chunks are returned, each with its payload metadata (file path, folder ID, source type).

3. Prompt Construction

The retrieved chunks are formatted with source citations and combined with the system prompt, conversation history, and user query into a GROQ API call:

SYSTEM: You are QA Buddy AI, a senior QA engineering assistant...
CONTEXT:
[Source 1 - selenium_repo/login_tests.py | Folder: 01]
...
[Source 2 - jira_tickets/BUG-421.json | Folder: 04]
...
HISTORY: (last 6 messages)
QUERY: How do I handle OAuth2 login in Selenium?

4. LLM Generation

GROQ's mixtral-8x7b-32768 generates the answer with a 32K context window, temperature 0.1 for deterministic outputs, and up to 4096 completion tokens. The response is streamed back to the frontend via SSE.

Data Ingestion

Ingestion runs as a local Python script (scripts/seed_qdrant.py) — not on Vercel. This is because:

  • Vercel serverless functions have a 50MB payload limit and 30s timeout
  • Processing 5000+ test cases, code files, and PDFs requires more time and memory
  • The script only needs to run when data changes, not on every request

Ingestion Flow

  1. Read all files from the 10 data folders
  2. Chunk each file based on its type (code by function, CSV per row, MD by heading, etc.)
  3. Generate embeddings via OpenAI batch API (20 at a time)
  4. Build PointStruct objects with chunk text + metadata
  5. Upsert all points to Qdrant Cloud collection

Metadata Schema

Every chunk stored in Qdrant includes:

{
  "content": "chunk text content",
  "file_path": "relative/path/to/file",
  "folder_id": "01-10",
  "source": "selenium_repo | playwright_repo | test_cases | ...",
  "language": "python | java | csv | text | ..."
}

Chunking Strategy

Different data types require different chunking strategies. A single chunk size would lose meaning for code, duplicate test cases, or miss context in logs.

Data TypeStrategyRationale
Code (.py, .java, .js)Function/class boundariesCode is meaningless mid-function. Each function is a natural atomic unit.
CSV/XLSX Test CasesOne row per chunkTest cases are atomic. Never split a single test case across chunks.
Markdown DocsPer heading (## / ###)Respects document structure. Each section is a self-contained unit.
Plain text / LogsSliding window 768/150Overlap preserves context across chunk boundaries. Logs use 512/100.
PDFsText extraction + sliding windowPyMuPDF extracts text, then chunked at 768/150.

Deployment

The application is deployed to Vercel using the standard Vercel Python + static build pipeline.

Deployment Steps

  1. Push the repository to GitHub
  2. Connect the GitHub repo in Vercel dashboard
  3. Set environment variables in Vercel project settings
  4. Deploy — Vercel detects vercel.json and builds accordingly
  5. Run python scripts/seed_qdrant.py locally to seed Qdrant Cloud

vercel.json

{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "installCommand": "pip install -r requirements.txt",
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api/index.py" },
    { "source": "/(.*)", "destination": "/index.html" }
  ],
  "functions": {
    "api/index.py": { "maxDuration": 30 }
  }
}

The Python runtime uses Flask wrapped as a WSGI application. Vercel automatically detects the app variable in api/index.py and serves it as a serverless function. Static assets (dist/) are served from Vercel's edge CDN.
