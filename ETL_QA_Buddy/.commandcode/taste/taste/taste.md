# Taste
- Prefers the assistant to directly execute git operations (commit and push to the remote) on their behalf when asked to sync code, rather than being given manual instructions to run themselves. Confidence: 0.85
- Expects a bug fix to be delivered as a complete loop: fix the code, commit, push, redeploy the affected service, and verify the fix works on the live deployment (not just locally) before reporting done — e.g., "correct that, git commit push the code and redeploy". Confidence: 0.85
- Refers to the deployed product loosely (e.g., calling the whole app "the vercel app" even though the backend runs on Render) and expects the assistant to redeploy whichever service actually hosts the changed code and briefly clarify the platform split. Confidence: 0.7
- Prefers the assistant to handle deployment end-to-end on their behalf — providing API keys/tokens for each platform (Vercel token, Render API key, OpenAI API key) so the assistant can deploy, wire up env vars, verify, and report back the resulting production URLs, rather than receiving manual step-by-step instructions. Confidence: 0.95
- Communicates tasks tersely, sometimes with no instruction at all (e.g., just pasting an API key into chat, or a short status update like "now credit added to that open API key"), expecting the assistant to infer the intended action — such as swapping the key into the deployed service's env vars, or re-verifying that a previously-blocked feature now works end-to-end and reporting the result. Confidence: 0.9
- Tends to accept the assistant's recommended option when presented with multiple-choice decisions (e.g., picking the recommended hosting platform, choosing to provide an API key for automated deployment, and replying "yes please add" to the offer to document the latest fix in the README), expecting the assistant to proceed accordingly. Confidence: 0.7
- When asking about the state of deployed assets — whether the deployed app has the latest fix ("is the app ready?"), whether a deployed URL is publicly accessible/shareable ("is vercel app link public?"), or whether the git repo itself is public ("is the gitrepo public?") — expects the assistant to verify empirically (HTTP status, platform protection/SSO settings, deployment commit hashes, unauthenticated GitHub API calls, live end-to-end behavior) and report concrete evidence rather than asserting from memory, including any caveats like open CORS, public env vars, or security implications of a public repo. Confidence: 0.95
- Treats README documentation and screenshots as part of the deliverable that must stay in sync with code changes: asks whether they're updated after features/fixes land, and expects the assistant to confirm their freshness with concrete evidence — git status, commit hashes, and referenced image files — rather than asserting from memory, and to flag (and offer to fix) anything stale like a missing changelog note for the latest fix. Confidence: 0.7
